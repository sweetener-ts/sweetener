# Sweetener 0.1.0-alpha.8

This alpha fixes three bugs in what an expansion prints, all found by handing
the playground's generated code to TypeScript, which nothing had done before.
One of them was a silent miscompile. Package names, entry points, language
version, and format versions remain unchanged from alpha.7.

## Correctness

- A capture's line break no longer ends the statement a template wrote it
  into. A call site that broke the line in front of an expression --

  ```ts
  match (event) {
    { kind: "click" } =>
      `click`,
  }
  ```

  -- carried that break into a template's `return $body;`, where `return` was
  read as the whole statement and the arm returned `undefined`. The expansion
  type-checked only by accident of its return type, and nothing was reported.
  Where a template writes a placeholder on the same line as the token before
  it, the template's spelling of that seam now stands.

  A comment written in front of the captured expression cannot give up its
  line break, so after `return`, `throw`, `yield`, `break`, `continue` and
  `async` it is hoisted onto a line of its own above the keyword. Everywhere
  else a call-site comment stays exactly where it was written.

- A generic arrow a template writes is printed `<T,>(value: T) => value`.
  A template is written in the file that defines its macro and printed into
  the file that invokes it, and `<T>(` is a generic arrow in `.ts` but an
  unclosed element in `.tsx`. A `.stsx` file using such a macro got output
  TypeScript rejects, and generated `.ts` broke wherever it was read as `.tsx`
  -- pasted into the TypeScript playground, for one. `async <T,>(` is also no
  longer spaced as a comparison.

- A prefix type assertion a template writes, `<A>value`, is printed
  `(value as A)`. It has no `.tsx` spelling at all, and `as` binds more
  loosely than the prefix did, so the parentheses come with it:
  `<A>-$value * 2` prints `((-3 as A) * 2)`.

Only what a template wrote is respelled. Code the author of a file wrote is
printed as they wrote it, as it always has been.

## Examples

- The playground build now type-checks every example's generated project with
  the real compiler and libraries, and requires every generated `.ts` file to
  parse as `.tsx`. An example whose output TypeScript rejects fails the build
  and the site deploy.
- The playground's `react-memoization` project declared React's compiler
  cache as `unknown[]`, which never type-checked; it now matches the checked
  copy of the example.

The remaining expansion, diagnostic, benchmark, and language follow-ups are
tracked in [the open issues](https://github.com/sweetener-ts/sweetener/issues).
