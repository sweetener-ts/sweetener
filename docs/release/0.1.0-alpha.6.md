# Sweetener 0.1.0-alpha.6

This alpha closes the reader and diagnostic follow-ups filed after alpha.4, two
of which were silent: valid TypeScript that expanded to something other than
what was written, with nothing reported. Package names, entry points, language
version, and format versions remain unchanged from alpha.5.

## Correctness

- A macro written in an object literal between a `<` and a `>` is expanded.
  `f(a < b, { x: twice(1) }, c > d)` is three comparisons, and the walk read
  the brace as an object type, so the invocation reached the emitted TypeScript
  as written and nothing said so.
- An annotation ending in `asserts` ends at the line break. `asserts` heads a
  type predicate only where the name it is about is written on its line; read
  as an unconditional type operator, `let a: asserts` took the statement under
  it into the annotation, and a macro written there never ran.
- A heritage clause broken before `async` reads the same way at statement level
  as at item level. `class C extends` and the `async.Base {}` under it are one
  class, as TypeScript reads them.
- Headers are read to their end rather than for a fixed number of nodes. A
  33-member union in an arrow's return type, a 16-member union in a function
  expression's, and a 17-segment heritage path in a class expression were each
  refused for standing past a count. An object type in a heritage clause's type
  arguments is no longer taken for the class body.
- `y?.<A>(b)`, an optional call with its type arguments supplied, is read.

## Diagnostics

- `// @ts-check` and `// @ts-nocheck` decide whether a held name will ever be
  answered, and are read. Before, a checked JavaScript file was warned about
  names TypeScript had already resolved, and an unchecked TypeScript file was
  assumed to answer -- so a name the emitted code does not define shipped with
  `check` reporting success and saying nothing.
- `SWR4024` no longer claims nothing defines a name where nothing checked the
  file. On an unchecked path it says what expansion knows: the name is written
  into the output as it stands, and this build does not check that file. On a
  checked path, where TypeScript has already reported it cannot find the name,
  the sentence is unchanged.

## Performance

- Expansion is about 4% faster over a three-hundred-file project and about 6%
  faster over a macro replacement of four thousand unparsed tokens, from
  removing allocation in the origin store, the closure scan, and macro
  resolution. Measured against a control, minimum of ten rounds.

## Tooling

- `pnpm test` refuses to record a result from a run that wrote none, rather
  than reading the previous run's report and stamping it with this commit.
- `pnpm status:check` fails when a recorded check predates the tree.
- `pnpm benchmark:check` fails on a scenario missing from the baseline instead
  of printing a line about it, and says when a baseline was recorded under
  conditions that make a pass weak evidence. A new `expansion/wide-replacement`
  scenario covers a macro replacement of thousands of unparsed tokens, which no
  scenario measured; it has no baseline row yet, so the check reports it as
  unmeasured until one is recorded.

The remaining expansion, diagnostic, benchmark, and language follow-ups are
tracked in [the open issues](https://github.com/sweetener-ts/sweetener/issues).
