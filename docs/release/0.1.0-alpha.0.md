# Sweetener 0.1.0-alpha.0

Status: staged and locally verified; npm publication and the annotated Git
release tag are not authorized and have not been performed.

This alpha is a TypeScript-first, declarative, hygienic macro compiler kernel.
It supports new syntax in expression, statement, item, binding, type,
class-element, and JSX-child contexts; lexical core rewrites; custom operators;
local/recursive/generated macros; official TypeScript check/emit; origins,
traces, source maps, incremental caches, and mapped editor reads.

## Release evidence

- 9 installable package tarballs at synchronized version `0.1.0-alpha.0`,
  each carrying the MIT licence and pointing at its source directory;
- SHA-256 and byte length for every tarball in
  `artifacts/release/release.json`;
- clean Node 24 installation with no private or `workspace:*` publish fields;
- two installed external workflows covering declarative expansion, runtime,
  check/build/watch, diagnostics, navigation, and safe rename;
- Node/TypeScript compatibility matrix;
- 13-scenario Node 24 benchmark baseline with raw samples;
- every documented host installed from packed tarballs into projects created
  from scratch, Bun, Rsbuild and Farm included;
- normative language/package/security/migration specification;
- full repository correctness, boundary, acceptance, specification, and sample
  gates.

## Publication procedure

1. Run `pnpm check` on Node 24.
2. Run `pnpm release:verify` on Node 24.
3. Inspect `artifacts/release/release.json` and tarball contents.
4. Obtain maintainer authorization and registry credentials. The `@sweetener`
   scope has to exist, and the publishing account needs a granular automation
   token held as the `NPM_TOKEN` secret.

   A trusted publisher is the better credential and needs no secret, but it is
   configured on a package's own settings page, so it cannot be set up for a
   name that has never been published. The first release uses the token; once
   these nine names exist, configure trusted publishing on each and delete the
   secret.

5. Run the Release workflow with `dryRun` set, and read what it would publish.
6. Create an annotated `v0.1.0-alpha.0` tag at the reviewed commit and push it.
   The workflow refuses a tag that does not match the staged version, publishes
   every tarball under the `alpha` dist-tag, and signs provenance with the
   workflow's own OIDC token.

## Publishing the next one

`0.1.0-alpha.0` went out with `NPM_TOKEN`, because a trusted publisher is
configured on a package's own settings page and the names did not exist yet.
They exist now, so the token can go.

For each of the nine packages, on npmjs.com under Packages, then the package,
then Settings, then Trusted publishing, add a GitHub Actions publisher:

| Field             | Value          |
| ----------------- | -------------- |
| Organization      | `sweetener-ts` |
| Repository        | `sweetener`    |
| Workflow filename | `release.yml`  |

npm does not check the configuration when you save it. A wrong field surfaces
only when a publish fails, so run the Release workflow with `dryRun` set before
trusting it.

Then delete the `NPM_TOKEN` secret. The workflow asks for `--provenance` only
when a token is present, because a trusted publisher attaches provenance
itself, and `id-token: write` is already on the job. Keep `registry-url` on
setup-node: the npm CLI detects an OIDC environment and uses it before falling
back to a token.

Steps 4–6 are deliberately not performed by the local verifier. The version
they publish is the one in the root `package.json`, which
`npm version --no-git-tag-version` is what moves.
